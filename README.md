## Что умеет библиотека

- Держит одно соединение с брокером на сервис и само переподключается. После обрыва связи библиотека восстанавливает подписки и заново публикует свои устройства.
- Публикует свои устройства по [конвенции Wiren Board](https://github.com/wirenboard/conventions). Сервис описывает устройство и контролы, а мету, значения, ошибки, команды из `/on` и стирание топиков берёт на себя библиотека.
- Читает чужие устройства, то есть устройства других драйверов. Их значения, мета и ошибки обновляются в объектах сами, запись в них уходит командой в `/on`.
- Вызывает обработчики событий, назначенные на объекты, в том числе на контролы, которых ещё нет. У каждого обработчика своя очередь, события доходят по порядку.
- Работает с топиками вне конвенции через сырые методы.

Библиотека асинхронная, на asyncio и [aiomqtt](https://github.com/empicano/aiomqtt). Соединение идёт по MQTT 5.


## Быстрый старт

Сервис публикует своё устройство с порогом и аварией и следит за средней нагрузкой процессора, которую публикует wb-mqtt-metrics. Когда нагрузка выше порога, авария включается. Порог пользователь меняет в веб-интерфейсе. Пример написан как модуль сервиса `wb-mqtt-load-alarm`, который подключил библиотеку по разделу [Подключение к сервису](#подключение-к-сервису).

```python
import asyncio
import contextlib
import logging
import signal
import sys
from typing import Any

from wb.mqtt_load_alarm.wb_mqtt_lib import (
    BrokerDisconnectedError,
    Client,
    Control,
    ControlType,
    LoginRejectedError,
)

logger = logging.getLogger(__name__)

THRESHOLD_MIN = 0
THRESHOLD_MAX = 10


async def run() -> None:
    async with Client(driver="wb-mqtt-load-alarm") as client:
        try:
            device = await client.create_device("load_alarm", title={"en": "Load Alarm", "ru": "Нагрузка"})
            threshold = await device.create_control(
                "threshold",
                control_type=ControlType.RANGE,
                title={"en": "Threshold", "ru": "Порог"},
                minimum=THRESHOLD_MIN,
                maximum=THRESHOLD_MAX,
                value=2,
            )
            alarm = await device.create_control(
                "alarm",
                control_type=ControlType.ALARM,
                title={"en": "High Load", "ru": "Высокая нагрузка"},
                readonly=True,
                value=False,
            )
            load = await client.get_control("metrics/load_average_1min")

            async def threshold_command(control: Control, value: Any) -> None:
                if isinstance(value, (int, float)) and THRESHOLD_MIN <= value <= THRESHOLD_MAX:
                    await control.set_value(value)

            async def check(control: Control, value: Any, previous: Any) -> None:
                if load.value is not None:
                    await alarm.set_value(load.value > threshold.value)

            threshold.on_command(threshold_command)
            load.on_value(check)
            threshold.on_value(check)

            # Ждёт, пока обработчик сигнала не отменит главную задачу
            await asyncio.Future()
        finally:
            # Без связи остатки уберёт create_device при следующем старте
            with contextlib.suppress(BrokerDisconnectedError):
                await client.remove_driver_devices()


async def main() -> int:
    task = asyncio.current_task()
    loop = asyncio.get_running_loop()
    for signal_number in (signal.SIGTERM, signal.SIGINT):
        loop.add_signal_handler(signal_number, task.cancel)
    try:
        await run()
    except asyncio.CancelledError:
        return 0
    except LoginRejectedError as error:
        # Повторы не помогут
        logger.error("MQTT broker rejected the login: %s", error)
        return 2
    return 0


if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)
    sys.exit(asyncio.run(main()))
```

- `create_device` и `create_control` публикуют своё устройство. Если под тем же именем остались топики прошлого запуска этого же драйвера, библиотека сначала их стирает.
- `get_control` отдаёт объект чужого контрола сразу, даже если wb-mqtt-metrics ещё не запустился. Значение в объекте появится, когда драйвер его опубликует.
- `on_value` срабатывает сразу при назначении с текущим значением, поэтому начальное состояние сервис считает без отдельного чтения. Функция `check` назначена на два объекта и срабатывает, когда меняется любой из них.
- `threshold.set_value` публикует значение, потому что устройство своё. Запись в чужой контрол ушла бы командой в `/on`.
- Команда приходит в `threshold_command` значением по типу контрола, но тип и пределы обработчик проверяет сам. Команду в `/on` может прислать правило или другой сервис.
- Python по умолчанию завершается на SIGTERM сразу, без выхода из `async with`, поэтому сервис ставит свой обработчик сигнала. Он отменяет главную задачу, и `await asyncio.Future()`, которое иначе ждёт бесконечно, заканчивается.
- Если сигнал пришёл, пока клиент ещё ждёт брокер на входе в `async with`, ожидание прерывается, и сервис выходит. Если клиент уже подключён, сначала `finally` стирает устройства сервиса, а потом выход из `async with` закрывает клиент.


## Подключение к сервису

Библиотеке нужны Python 3.13 и aiomqtt 2.x. На контроллере это Debian trixie с пакетами `python3` 3.13 и `python3-asyncio-mqtt` 2.3.1.

Сабмодуль кладут в корень репозитория сервиса, а при установке библиотека попадает внутрь пакета сервиса, например в `wb.mqtt_example.wb_mqtt_lib`. Так разные сервисы на одном контроллере работают каждый на своей версии и не конфликтуют за файлы в `dist-packages`.

```bash
# Относительный URL раскрывается от адреса репозитория сервиса в организации wirenboard
git submodule add ../wb-mqtt-python-lib.git wb-mqtt-python-lib
# Закрепить нужную версию библиотеки
git -C wb-mqtt-python-lib checkout <коммит>
# В коммит сервиса попадает файл .gitmodules и хэш сабмодуля
git add .gitmodules wb-mqtt-python-lib
```

В `setup.py` сервиса пакет библиотеки добавляют к пакетам сервиса.

```python
from setuptools import find_namespace_packages, setup

LIB_PACKAGE = "wb.mqtt_example.wb_mqtt_lib"

setup(
    name="wb-mqtt-example",
    packages=find_namespace_packages(include=["wb.*"]) + [LIB_PACKAGE],
    package_dir={LIB_PACKAGE: "wb-mqtt-python-lib/wb_mqtt_lib"},
)
```

Сервис импортирует библиотеку из своего пакета.

```python
from wb.mqtt_example.wb_mqtt_lib import Client, ControlType
```

Остальное в репозитории сервиса.

- В `debian/control` в `Depends` нужен `python3-asyncio-mqtt`, сабмодуль свои зависимости сам не приносит. Если тесты сервиса при сборке импортируют библиотеку, тот же пакет нужен и в `Build-Depends`.
- Клон сервиса делают с `--recurse-submodules` или после клона вызывают `git submodule update --init`.

Библиотеку проверяет её собственный CI. Чтобы Jenkins не проверял её линтерами сервиса, в `Jenkinsfile` сервиса добавляют `defaultPythonChecksExcludes: 'wb-mqtt-python-lib'`.

Новая версия библиотеки доходит до сервиса только бампом сабмодуля.

```bash
# Забрать новые коммиты библиотеки
git -C wb-mqtt-python-lib fetch
# Перейти на нужный коммит
git -C wb-mqtt-python-lib checkout <коммит>
# В PR сервиса будет видна только смена хэша
git add wb-mqtt-python-lib
```


## Клиент

```python
Client(driver: str, broker_url: str = DEFAULT_BROKER_URL)
```

`Client` держит одно соединение с брокером всё время работы сервиса. `driver` это имя драйвера сервиса. Оно уходит в мету каждого своего устройства и в идентификатор клиента MQTT, а по нему `remove_driver_devices()` находит устройства сервиса, в том числе оставшиеся от прошлого запуска.

По умолчанию `broker_url` равен `unix:///var/run/mosquitto/mosquitto.sock`, это брокер контроллера. Адрес другого брокера пишется так.

- `tcp://host:port`. `mqtt-tcp://host:port` значит то же самое.
- `ws://host:port/path`. Путь уходит в запрос websocket, без него клиент идёт на `/mqtt`.
- `unix:///path/to/socket`, путь после трёх косых. Адрес `unix://` с хостом указал бы на другой сокет и даёт `ValueError`.
- Логин и пароль пишутся перед хостом, `tcp://user:password@host:1883`. Символы `/`, `?`, `#`, `@`, `:` и `%` в них кодируются процентами, например `%2F` вместо `/`. В пароле допустим любой символ. Логин с управляющим символом даёт `ValueError`, на таком логине mosquitto рвёт соединение, и клиент переподключался бы постоянно.

Неверный адрес, в том числе с незакодированными `?` или `#`, даёт `ValueError` сразу при создании клиента. Текст ошибки адрес не цитирует, в нём может быть пароль. Соединения `tcp://` и `ws://` не шифруются, логин и пароль идут по сети открытым текстом.

Вход в `async with` ждёт первого соединения и повторяет попытки, пока брокер не ответит. Ограничить ожидание можно через `asyncio.wait_for(client.connect(), timeout)`, после `TimeoutError` клиент не переподключается в фоне и освобождает имя драйвера. Начатая попытка доходит до конца сама, это до 5 с, а следующий `connect()` или `close()` её дожидается.

Если брокер отверг логин или пароль при первом подключении, вход бросает `LoginRejectedError`, и клиент больше не переподключается. После первого соединения клиент переподключается сам при любом обрыве, в том числе когда брокер отвергает логин. Пауза между попытками растёт от 0,5 до 30 с.

Сервису обычно хватает одного клиента. Второй нужен только для устройств под другим именем драйвера, устройства одного клиента для другого чужие. Второй клиент с тем же драйвером в том же процессе получит `ValueError`, пока первый не закрыт.

Своё устройство у того клиента, который его создал. Устройство другого процесса с тем же именем драйвера `create_device` под тем же именем считает остатками своего драйвера и стирает, а `remove_driver_devices()` стирает все такие устройства. Поэтому у каждого процесса своё имя драйвера. Для другого процесса устройства сервиса чужие, он меняет их командами в `/on`.

`client.connected` показывает, есть ли сейчас связь с брокером. Команда чужому контролу без связи не копится до переподключения, а сразу бросает `BrokerDisconnectedError`, поэтому эту ошибку ловят, а не проверяют `connected` заранее. Своё значение без связи ошибки не даёт, библиотека опубликует его после переподключения.

`client.on_connection_change(handler)` сообщает о смене связи. Свои устройства и подписки библиотека восстанавливает сама, а событие нужно сервису, который сам что-то делает при обрыве. Например, он помечает устройства внешней системы недоступными, а после возврата связи запрашивает её состояние.

```python
async def link_changed(connected: bool) -> None:
    if connected:
        await bridge.request_state()
    else:
        await bridge.mark_unavailable()


client.on_connection_change(link_changed)
```

- `True` приходит после каждого подключения, когда клиент уже восстановил подписки. Обработчик, назначенный до `connect()` или до запуска цикла событий, получит `True` при первом подключении.
- `False` приходит один раз на обрыв, сколько бы неудачных попыток переподключения ни было после него.
- До первого подключения и при `close()` события нет.
- При назначении обработчик не вызывается, текущее состояние видно в `client.connected`.

Выход из `async with` или `close()` закрывает клиент. Клиент отменяет свои обработчики и фоновые задачи, даже если они ждут брокер, и `except Exception` эту отмену не ловит. Потом он закрывает соединение. Свои устройства остаются в брокере, удалить их сервис может сам перед выходом, как в [быстром старте](#быстрый-старт). Свои изменения, которые не дошли до брокера, например из-за обрыва связи, теряются.

Вызовы библиотеки, которые в это время ждут брокер в другом коде, например в главной задаче сервиса, бросают `ClientClosedError`. Обычно сразу, а если связь уже не работает, но обрыв ещё не замечен, в течение 5 с.

Отмена вызова `close()` прерывает только его ожидание, закрытие клиента доходит до конца, а следующий `close()` ждёт его. Повторный `close()` из обработчика или фоновой задачи этого клиента возвращается сразу, не дожидаясь конца закрытия, поэтому его можно звать и в `finally` фоновой задачи.

Закрытый клиент снова не подключить. Для нового соединения нужен новый `Client`, и он начинает без устройств, подписок и обработчиков.

Если у сервиса свой жизненный цикл, например объект с методами `start` и `stop` или фикстура в тестах, клиент держат без `async with` и сами вызывают `connect()` и `close()`.

```python
class Service:
    def __init__(self, broker_url: str) -> None:
        self._client = Client(driver="wb-mqtt-example", broker_url=broker_url)

    async def start(self) -> None:
        await self._client.connect()
        device = await self._client.create_device("example", title="Example")
        relay = await device.create_control("relay", control_type=ControlType.SWITCH, value=False)
        relay.on_command(self._relay_command)

    async def stop(self) -> None:
        with contextlib.suppress(BrokerDisconnectedError):
            await self._client.remove_driver_devices()
        await self._client.close()

    async def _relay_command(self, control: Control, value: Any) -> None:
        if isinstance(value, bool):
            await control.set_value(value)


async def main() -> int:
    task = asyncio.current_task()
    loop = asyncio.get_running_loop()
    for signal_number in (signal.SIGTERM, signal.SIGINT):
        loop.add_signal_handler(signal_number, task.cancel)
    service = Service(DEFAULT_BROKER_URL)
    try:
        await service.start()
        await asyncio.Future()
    except asyncio.CancelledError:
        return 0
    finally:
        await service.stop()
```

`stop()` вызывают в `finally`, тогда он закроет клиент и в том случае, когда `start()` упал на середине. Сигнал отменяет главную задачу, как в [быстром старте](#быстрый-старт). Клиент можно создать до запуска цикла событий, подключается он в `connect()`. До подключения чтения брокера и события бросают `BrokerDisconnectedError`, а `raw.subscribe` и retained `raw.publish` сработают после подключения. Повторный `connect()` подключённого клиента бросает `RuntimeError`.


## Свои и чужие устройства

Свои и чужие устройства описываются одними классами `Device` и `Control`, обращение идёт по имени «устройство/контрол». Объект хранит только имя, а мету, значения, ошибки и обработчики держит клиент. Поэтому все объекты одного контрола видят одно и то же, и объект остаётся рабочим, когда драйвер устройства перезапускается или клиент переподключается к брокеру. Объекты одного контрола равны по `==`, но это разные объекты, поэтому `is` для сравнения не годится.

|                                                        | Своё                                                    | Чужое                                                                       |
| ------------------------------------------------------ | ------------------------------------------------------- | --------------------------------------------------------------------------- |
| Откуда состояние                                       | из кода сервиса, библиотека его публикует               | из брокера                                                                  |
| `control.set_value(value)`                             | локальное значение обновляется сразу, retained публикуется, если MQTT-строка изменилась | команда в `/on`, `control.value` изменится, когда драйвер выполнит команду |
| `set_error`, `update_meta`, `remove`, `create_control` | публикуют и стирают топики                              | бросают `NotOwnError`                                                       |
| `on_command`, `on_control_command`                     | команды из `/on`                                        | бросают `NotOwnError`                                                       |
| Когда приходят события                                 | в момент вызова в коде сервиса                          | когда из брокера пришло сообщение драйвера                                  |
| После переподключения                                  | библиотека публикует устройство заново                  | обработчики получают изменения за время обрыва, стёртого за обрыв библиотека не видит, раздел [Чужие устройства](#чужие-устройства) |
| Устройство изменили извне                              | библиотека не замечает, раздел [Правки извне](#правки-извне) | обработчики получают правку                                             |

Классы `Device` и `Control` нужны сервису для аннотаций типов. Сами объекты дают клиент и устройство, это `create_device`, `create_control`, `get_device`, `get_control` и `device.controls`, а ещё обработчик получает объект аргументом. Сервис объекты сам не создаёт, вызов `Device(client, "dev")` бросает `TypeError`.

Объект привязан к имени устройства, а не к владельцу. Если чужое устройство пропало и сервис создал своё под тем же именем, обработчики, назначенные на чужое, продолжают работать уже со своим. После `remove()` своего устройства обработчики остаются. Устройство другого драйвера, которое потом появится под этим именем, они увидят, только если сервис запрашивал его через `get_control` или `get_device`, пока оно было чужим. Иначе устройство нужно запросить заново.


## Свои устройства

```python
device = await client.create_device("waterius_1", title={"en": "Waterius 1", "ru": "Ватериус 1"})
cold = await device.create_control(
    "cold_water",
    control_type=ControlType.VALUE,
    title={"en": "Cold Water", "ru": "Холодная вода"},
    units="m^3",
    precision=0.001,
    readonly=True,
    value=0.0,
)
await cold.set_value(12.3456)  # уйдёт как «12.346»
```

### Создание устройства

`client.create_device(name, title=None, force=False)` сначала смотрит, что лежит в брокере под этим именем. Если там остались топики своего драйвера, например от прошлого запуска с другим набором контролов, библиотека их стирает, и устройство начинается с чистого листа. Потом она публикует мету устройства с именем драйвера клиента. Драйвер устройства в брокере библиотека берёт из меты, а если его там нет, из старого подтопика `/meta/driver`.

Если под именем лежит устройство другого драйвера, устройство без драйвера или одни контролы с метой без меты устройства, `create_device` бросает `DeviceTakenError` и ничего не трогает. Топики, из которых не собирается устройство, библиотека считает остатками и стирает. Это, например, одни значения без меты, мета только подтопиками без `/meta/driver` или битая мета. Сервис сам выбирает имя, не занятое чужими топиками.

С `force=True` библиотека стирает всё под именем, в том числе чужое, и публикует своё устройство. Это нужно, например, после смены имени драйвера. Другой драйвер, если он ещё работает, продолжит публиковать туда свои значения, а после своего переподключения опубликует и мету. Разово `force=True` нужен и сервису, который переходит на библиотеку со своего MQTT-кода, если оборванная уборка прежней версии оставила под именем одни контролы без меты устройства.

Без связи `create_device` бросает `BrokerDisconnectedError`. Повторное создание уже созданного устройства бросает `ValueError`.

Устройство без контролов в веб-интерфейсе показывается пустой карточкой, пока сервис не создаст первый контрол.

### Создание контрола

`device.create_control(name, control_type, ...)` публикует мету контрола и начальное значение, если оно передано. Всё объявление проверяется до публикации, ошибка в любом поле не оставляет в брокере ничего.

- `name` — имя контрола.
- `control_type` — тип контрола из `ControlType`.
- `title` — заголовок, строка считается английской, на двух языках это `{"en": "...", "ru": "..."}`.
- `units` — единицы измерения для `value` и `range`, строка.
- `precision` — положительное число. MQTT-значение публикуется с тем же числом знаков после запятой, что у `precision`, а веб-интерфейс использует его как шаг поля ввода.
- `minimum`, `maximum` — пределы для `range` и `value`, конечные числа.
- `order` — место на карточке, целое число, по умолчанию по порядку создания.
- `readonly` — `True`, если контрол не принимает команды. Это подсказка веб-интерфейсу, он не даёт менять такой контрол. Команды в `/on` от правил и других сервисов всё равно приходят, и `on_command` их получает.
- `hidden` — `True`, чтобы спрятать контрол в веб-интерфейсе.
- `enum` — названия значений, `{"0": {"en": "Idle", "ru": "Ожидание"}, "1": ...}`.
- `value` — начальное значение. Без него веб-интерфейс до первого `set_value` показывает заглушку, например `0` у числа и выключенный выключатель. У `pushbutton` значения нет, и любое `value` даёт `TypeError`.

`readonly` и `hidden` библиотека пишет в мету всегда, даже когда они `False`.

В `ControlType` десять действующих типов конвенции, это `SWITCH`, `WO_SWITCH`, `ALARM`, `PUSHBUTTON`, `RANGE`, `RGB`, `TEXT`, `LOCAL_TIME`, `W1_ID` и `VALUE`. Устаревшие типы вроде `temperature` создать нельзя, вместо них конвенция рекомендует использовать `value` с `units`. Элемент `ControlType` равен своей строке, поэтому `control.control_type == ControlType.SWITCH` работает и для чужого контрола, у которого тип пришёл из брокера строкой.

Имена устройств и контролов проверяются до первой публикации. Пустое имя, имя с `/`, `+`, `#` или управляющими символами и слишком длинное имя дают `ValueError`.

### Значения

`control.set_value(value)` проверяет значение по типу контрола, какие значения принимает каждый тип, показано в таблице раздела [Поля объектов](#поля-объектов). Новое значение своего контрола сразу попадает в `control.value` и в события, а в MQTT уходит, только если изменилась строка в топике. У `pushbutton` публикуется каждое нажатие. Для чужого контрола значение уходит командой в `/on`.

Изменения уходят в брокер в порядке вызовов, в том числе из разных задач.

`set_value(None)` стирает значение своего контрола любого типа, кроме `pushbutton`. Библиотека публикует пустое retained-сообщение, `control.value` становится `None`, события нет.

Число с `precision` уходит с тем числом знаков после запятой, сколько их в `precision`, без нулей в хвосте. При `precision=0.1` значение 21.54 уходит как «21.5», а `control.value` и событие получают 21.54. Число без `precision` уходит кратчайшей записью без экспоненты, 21.0 как «21», 1e16 как «10000000000000000».

### Ошибки, мета и удаление

- `control.set_error(error)` ставит или снимает ошибку контрола, `device.set_error(error)` ошибку самого устройства. Ошибка это флаги `ControlErrorFlags.READ`, `WRITE` и `POLL`, их складывают через `|`, а `ControlErrorFlags.NONE` снимает ошибку. Сама библиотека ошибку не снимает, в том числе при записи значения. Ошибку устройства веб-интерфейс показывает красной карточкой. На контролы библиотека её не переносит, если это нужно, сервис ставит ошибку и им. Ошибка не из `ControlErrorFlags` даёт `TypeError` до изменения состояния.
- `control.update_meta(**fields)` меняет поля меты на ходу, без пересоздания контрола, например `await control.update_meta(readonly=True)`. Поля те же, что у `create_control`, кроме имени, типа и значения. Тип меняют пересозданием, `control.remove()` и снова `device.create_control`, обработчики контрола при этом остаются. Поле, которому передали `None`, уходит из меты, открытая страница веб-интерфейса покажет это только после перезагрузки. `readonly` и `hidden` принимают только `True` и `False`. Если поля не изменились, библиотека ничего не публикует.
- `device.update_meta(title)` меняет заголовок устройства.
- `control.remove()` и `device.remove()` стирают пустыми retained-сообщениями всё, что клиент сам опубликовал под контролом или устройством, в том числе старые подтопики меты, опубликованные через `raw.publish`. Без связи стирание уходит после переподключения. Устройство стирается этапами, каждый после того, как брокер подтвердил предыдущий, мета устройства с именем драйвера уходит последней. Повторный вызов ничего не делает, `control.remove()` после `device.remove()` тоже.
- `client.remove_driver_devices()` разово находит в брокере все устройства с драйвером этого клиента, по мете и по подтопику `/meta/driver`, стирает их, включая созданные в этом запуске, и возвращает список их имён. Отменённый `create_device` всё равно доделывает устройство, поэтому `remove_driver_devices()` сначала ждёт такие создания и стирает и эти устройства, как при остановке сервиса из [быстрого старта](#быстрый-старт). Он стирает и устройства другого процесса с тем же драйвером. Без связи бросает `BrokerDisconnectedError`.

Если сервис упадёт посреди удаления, мета устройства с именем драйвера останется, потому что она стирается последней. Следующий `create_device` с тем же именем или `remove_driver_devices()` её найдут.

После `device.remove()` действия владельца с устройством, `set_value`, `set_error`, `update_meta` и `create_control`, бросают `ControlMissingError`. `on_command` назначить можно, обработчик заработает, когда сервис создаст устройство заново.

### Правки извне

Своё устройство библиотека в брокере не слушает. Если устройство удалили в веб-интерфейсе, поменяли его мету или другой сервис опубликовал мету со своим драйвером, библиотека этого не замечает, объекты не меняются, событий нет. После переподключения клиент публикует своё устройство заново. Запись прямо в топик значения своего контрола библиотека тоже не видит.


## Чужие устройства

```python
relay = await client.get_control("wb-mr6c_10/K1")
await relay.set_value(True)  # команда в /devices/wb-mr6c_10/controls/K1/on
```

| Вызов                                     | Что делает                                                                                                                  |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `client.get_control(name)`                | подписывается на устройство, ждёт ответа брокера и отдаёт объект контрола, даже если контрола нет                           |
| `client.get_control(name, timeout=60)`    | то же, но ждёт появления контрола до 60 секунд, иначе бросает `TimeoutError`                                                |
| `client.get_device(name, timeout=None)`   | то же для устройства                                                                                                        |
| `client.get_device_names()`               | отдаёт имена устройств, которые сейчас есть в брокере, подписка только на время чтения                                      |
| `client.get_device_snapshot(name)`        | отдаёт снимок устройства `DeviceSnapshot`, который потом не меняется, или `None`, если устройства нет. Подписка только на время чтения |
| `await control.wait_value(expected, timeout)` | ждёт, пока значение станет равным `expected` или переданная функция вернёт истину, раздел [Порядок событий и фоновые задачи](#порядок-событий-и-фоновые-задачи) |

Без `timeout` `get_control` и `get_device` ждут, пока брокер отдаст всё, что хранит по устройству, и возвращаются, есть контрол или нет. Если контрола нет, объект приходит с `exists = False`, а `on_added` сработает, когда контрол появится.

`get_control` и `get_device` подписываются на всё устройство, даже если сервис запросил один контрол. Повторный запрос того же устройства новой подписки не создаёт, подписка живёт до `close()`. Старые подтопики меты вроде `/meta/type` библиотека не читает.

Устройство существует, пока у него есть мета или хоть один контрол с метой. Только что появившееся устройство может быть ещё без контролов, драйвер публикует их следом.

Когда драйвер стирает мету контрола, например при своём перезапуске, обработчики остаются, `exists` становится `False`, `value` равно `None`, а `set_value` бросает `ControlMissingError`. Когда драйвер опубликует контрол снова, объекты снова увидят мету и значение.

Что драйвер стёр, пока у клиента не было связи, библиотека не видит. Удалённое за это время устройство или контрол остаётся с `exists = True`, стёртое значение и снятая ошибка остаются прежними, событий нет. Так до следующей публикации драйвера, и так же после перезапуска брокера, пока драйвер ещё не вернулся.

`set_value` чужого контрола с `readonly` отправляет команду как обычно, примет ли её драйвер, решает он сам.

`DeviceSnapshot` содержит `name`, `title`, `driver`, `error` и `controls`, словарь «имя → `ControlSnapshot`», а у каждого `ControlSnapshot` есть `meta`, `value` и `error`. Контролы без меты в снимок не попадают, у `pushbutton` значения нет.

Чужое устройство удалить нельзя, `remove()` бросает `NotOwnError`. Если сервис сам занимает это имя, хватит `create_device(name, force=True)`. Убрать чужие топики можно сырыми методами, рецепт в разделе [Работа с MQTT вне конвенции](#работа-с-mqtt-вне-конвенции).


## Поля объектов

| Поле           | Объект     | Что это                                                                                                       |
| -------------- | ---------- | ------------------------------------------------------------------------------------------------------------- |
| `name`         | оба        | имя, «K1» у контрола и «wb-mr6c_10» у устройства                                                              |
| `full_name`    | контрол    | «wb-mr6c_10/K1»                                                                                               |
| `device`       | контрол    | объект устройства                                                                                             |
| `controls`     | устройство | словарь «имя → контрол» из контролов, которые есть сейчас                                                     |
| `exists`       | оба        | у контрола есть мета, у устройства есть мета или хоть один контрол                                            |
| `is_own`       | оба        | устройство создал этот клиент и ещё не удалил                                                                 |
| `value`        | контрол    | значение в типе Python по таблице ниже                                                                        |
| `error`        | оба        | `ControlErrorFlags`, без ошибки `ControlErrorFlags.NONE`, а он в условии ложен, поэтому пишут `if control.error:` |
| `title`        | оба        | `TranslatedTitle`, заголовок `title.ru` и `title.en`. `title.get("ru", control.name)` отдаёт текст на нужном языке, без него на другом, а без обоих запасной текст, так заголовок показывает веб-интерфейс |
| `driver`       | устройство | имя драйвера из меты                                                                                          |
| `control_type`, `units`, `readonly` | контрол | поля меты                                                                                  |
| `meta`         | контрол    | `ControlMeta` со всеми полями меты, в том числе `precision`, `minimum`, `maximum`, `order`, `hidden` и `enum` |

`TranslatedTitle`, `ControlMeta` и `ControlErrorFlags` импортируются из библиотеки, например для аннотаций типов.

Значения по типам контрола одни и те же в `control.value`, в событиях и в командах, и `set_value` принимает их же.

| Тип контрола                                                       | Значение в Python                                                                 | В топике                          |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------- | --------------------------------- |
| `switch`, `alarm`, `wo-switch`                                     | `True` или `False`                                                                | `1` или `0`                       |
| `value`, `range` и устаревшие числовые типы вроде `temperature`    | конечное число, `int` или `float`                                                 | число, округлённое по `precision` |
| `local_time`, `w1-id`                                              | `int`                                                                             | целое                             |
| `rgb`                                                              | три целых от 0 до 255, в `control.value` кортеж                                   | `255;0;10`                        |
| `text`                                                             | `str`, а `set_value` принимает любое значение и пишет `str(value)`                | строка                            |
| `pushbutton`                                                       | значения нет, `control.value` всегда `None`. Нажатие и команда приходят как `True`, `set_value` принимает только `True` | `1` без retained |
| неизвестный тип чужого контрола                                    | `str` как есть                                                                    | строка                            |

Значение другого типа, в том числе `0` или `1` вместо `bool` и `NaN` в числе, `set_value` не принимает и бросает `TypeError` до публикации. Строка из брокера, которая не разбирается по типу, остаётся строкой. Если у чужого контрола сменился тип, библиотека читает прежнюю строку по новому типу, и `value` меняется без `on_value`, приходит только `on_meta`. `value` равно `None`, если контрола нет или его мета уже пришла, а значение ещё нет.


## Обработчики событий

Обработчики назначаются на объекты методами `on_*`.

| Метод                                    | Объект       | Когда срабатывает                                           | Что получает обработчик    |
| ---------------------------------------- | ------------ | ----------------------------------------------------------- | -------------------------- |
| `on_added`                               | контрол      | у контрола появилась мета с типом                           | `control`                  |
| `on_removed`                             | контрол      | мета контрола стёрта                                        | `control`                  |
| `on_value`                               | контрол      | значение изменилось в брокере, у `pushbutton` каждое нажатие | `control, value, previous` |
| `on_error`                               | контрол      | ошибка изменилась                                           | `control, error, previous` |
| `on_meta`                                | контрол      | изменилось поле меты, например заголовок или `readonly`     | `control`                  |
| `on_command`                             | свой контрол | пришла команда в `/on`                                      | `control, value`           |
| `on_added`                               | устройство   | у устройства появилась мета или первый контрол с метой      | `device`                   |
| `on_removed`                             | устройство   | пропали и мета устройства, и последний контрол              | `device`                   |
| `on_meta`                                | устройство   | сменился заголовок или драйвер                              | `device`                   |
| `on_error`                               | устройство   | изменилась ошибка самого устройства                         | `device, error, previous`  |
| `on_control_added`, `on_control_removed` | устройство   | у устройства появился или пропал контрол                    | `control`                  |
| `on_control_value`                       | устройство   | изменилось значение любого контрола устройства              | `control, value, previous` |
| `on_control_error`                       | устройство   | изменилась ошибка любого контрола устройства                | `control, error, previous` |
| `on_control_meta`                        | устройство   | изменилась мета любого контрола устройства                  | `control`                  |
| `on_control_command`                     | своё устройство | пришла команда в `/on` любого контрола устройства        | `control, value`           |
| `on_connection_change`                   | клиент       | связь с брокером появилась или пропала                      | `connected`                |

Обработчик может быть обычной или асинхронной функцией. Первым аргументом он получает объект, на котором сработало событие, у `on_control_*` это контрол устройства. Поэтому одну функцию можно назначить на несколько объектов, а объект из аргумента годится ключом словаря. Обработчик связи получает только `connected`. Число аргументов библиотека проверяет при назначении и сразу бросает `TypeError`. Методы `on_*` отдают ту же функцию, поэтому работают и как декораторы.

```python
@sensor.on_value
async def sensor_changed(control: Control, value: Any, previous: Any) -> None: ...
```

### Срабатывание при назначении

Обработчики состояния срабатывают сразу при назначении, а дальше только на изменения.

- `on_value` и `on_control_value` срабатывают сразу с текущим значением и `previous=None`, если значение уже есть.
- `on_error` и `on_control_error` срабатывают сразу с текущей ошибкой, если контрол или устройство есть.
- `on_added` и `on_control_added` срабатывают сразу для контролов и устройства, которые уже есть.
- `on_removed`, `on_control_removed`, `on_meta`, `on_control_meta`, `on_command`, `on_control_command` и `on_connection_change` срабатывают только на события.

Если контрола нет в момент назначения, `on_removed` не срабатывает, он сообщает о пропаже, которая случилась после назначения. Есть ли контрол сейчас, видно по `control.exists`.

Значение и ошибка, которые пришли раньше меты, доходят до `on_value` и `on_error`, когда контрол или устройство появится.

Обработчик, которому первый вызов не нужен, например уведомление «дверь открылась», отсеивает его по `previous is None`. Значение чужого контрола после перезапуска его драйвера тоже приходит с `previous=None`, потому что, пока мета контрола была стёрта, его значение было `None`. После переподключения клиента к брокеру значение, которое изменилось за время обрыва, приходит с прежним значением в `previous`.

Контрол считается удалённым, только когда стёрли его мету, поэтому обрыв связи и перезапуск брокера удалением не выглядят. Удаление приходит только в `on_removed`, `on_value` при этом не вызывается. Для своих устройств событие приходит в момент вызова `remove()`.

### Команды

Команда приходит в `on_command` значением по типу контрола, по таблице из раздела [Поля объектов](#поля-объектов).

- У `switch` любое ненулевое число в `/on` означает `True`, например «2», а ноль `False`.
- Тело, которое не разбирается по типу, приходит строкой как есть, например «abc» в `range`. Поэтому обработчик, который записывает команду в контрол, проверяет тип, иначе `set_value` бросит `TypeError`, а библиотека запишет его в лог как ошибку обработчика.
- Пустое сообщение в `/on` обработчику не приходит.
- Команду контрола, на который не назначены ни `on_command`, ни `on_control_command` устройства, библиотека пропускает, и назначенный позже обработчик её не получит.
- Сообщение в `/on` с флагом retain библиотека не исполняет и стирает из брокера.

`device.on_control_command` получает команды всех контролов устройства одной очередью, по порядку. Значение после команды сервис публикует сам, когда её выполнит.

### Исключения в обработчиках

Исключение обработчика библиотека пишет в лог и разбирает следующие события дальше. Это касается и `CancelledError`, которую обработчик получил от задачи, отменённой другим кодом. `BrokerDisconnectedError` и `ControlMissingError` идут одной строкой WARNING, это обычные ситуации, пока перезапускается брокер или драйвер. Остальное идёт как ERROR с трассировкой.

### Обработчик объявляют один раз

Обработчики живут, пока сервис их не снимет. Пропажа и появление контрола их не трогают, поэтому обработчик чужого контрола работает и после перезапуска драйвера, а обработчик своего контрола работает и после `remove()` и создания заново.

Повторное назначение той же функции на тот же объект ничего не добавляет. Функция, объявленная внутри кода, который выполняется много раз, например при каждом создании устройства или в `on_added`, каждый раз новая и встаёт рядом с прежней. Такой обработчик объявляют один раз снаружи, а данные он берёт по имени объекта.

```python
# Неверно. После трёх созданий одного устройства одна команда вызовет toggle_command трижды
async def add(connection: Connection) -> None:
    device = await client.create_device(connection.name)
    toggle = await device.create_control("toggle", control_type=ControlType.PUSHBUTTON)

    async def toggle_command(control: Control, value: Any) -> None:
        await connection.toggle()

    toggle.on_command(toggle_command)
```

```python
# Верно. Функция одна, повторное назначение ничего не добавляет
connections: dict[str, Connection] = {}


async def toggle_command(control: Control, value: Any) -> None:
    await connections[control.device.name].toggle()


async def add(connection: Connection) -> None:
    device = await client.create_device(connection.name)
    connections[device.name] = connection
    toggle = await device.create_control("toggle", control_type=ControlType.PUSHBUTTON)
    toggle.on_command(toggle_command)
```

Связанные методы одного объекта равны, поэтому `relay.on_command(self._relay_command)` при повторном назначении тоже ничего не добавляет.

### Обработчик, который пишет в контрол

`on_value` срабатывает на каждое изменение значения, в том числе на запись из самого обработчика. Своё значение меняется сразу при `set_value`, а запись в чужой контрол уходит командой, драйвер её выполняет, и новое значение приходит из брокера. Если обработчик `on_value` каждый раз пишет в тот же контрол новое значение, он вызывает сам себя снова и снова и забивает брокер публикациями. Так же зацикливаются два обработчика, которые пишут в контролы друг друга.

```python
# Неверно. Каждая запись меняет значение и снова вызывает обработчик
async def toggle_back(control: Control, value: Any, previous: Any) -> None:
    await control.set_value(not value)
```

Запись того же значения, что уже стоит в контроле, события не даёт, на ней цикл и кончается. Поэтому обработчик, который поправляет значение, пишет только когда значение нужно поменять.

```python
# Верно. Записанное 30 придёт в обработчик ещё раз, и он ничего не запишет
async def limit(control: Control, value: Any, previous: Any) -> None:
    if value > 30:
        await control.set_value(30)
```

### Снятие обработчика

| Вызов                                                               | Что делает                                                                                                                                                                                                                    |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `control.remove_handler(handler)`, `device.remove_handler(handler)` | без `await`, снимает функцию со всех `on_*` объекта, подписка на устройство остаётся. У контрола это его события, у устройства его собственные события и `on_control_*`, в том числе `on_control_command`. `control.remove_handler` не трогает `on_control_*` устройства, а `device.remove_handler` не трогает ту же функцию на отдельном контроле |
| `client.remove_handler(handler)`                                    | без `await`, снимает функцию с `on_connection_change`                                                                                                                                                                         |
| `await client.raw.unsubscribe(handler)`                             | снимает сырой обработчик со всех его фильтров. Если у фильтра не осталось обработчиков, библиотека отписывается в брокере                                                                                                    |

Обработчик снимают той же функцией, которую передали при назначении, новая функция с тем же кодом не подойдёт. Лямбду, которую потом надо снять, сохраняют в переменную. События, которые обработчик ещё не начал разбирать, после снятия выбрасываются. Вызов, который идёт сейчас, отменяется на ближайшем `await`, кроме случая, когда обработчик снимает сам себя. Если обработчик поймал эту отмену, его вызов доходит до конца, следующих вызовов нет.


## Порядок событий и фоновые задачи

У каждого обработчика своя очередь. События одного обработчика идут по порядку, и следующее ждёт, пока предыдущий вызов закончится, включая все `await` внутри. Каждое событие доходит со своим значением и своим `previous`, ни одно не теряется. Разные обработчики друг друга не ждут, и порядок между ними не задан, поэтому обработчик берёт нужное состояние из объекта, другой обработчик к этому моменту мог ещё не отработать. Очередь заводится на объект, событие и функцию. Одна функция на двух объектах или на двух событиях одного объекта, например `on_added` и `on_meta`, это две очереди, и её вызовы могут пересечься на `await`.

Если обработчик медленнее потока событий, его очередь растёт, а при 100 ждущих событиях библиотека пишет предупреждение в лог.

Долгую работу, например сканирование шины на минуту, обработчик запускает через `client.start_task(coroutine)` и сразу возвращается, тогда следующие события его очереди, например команда отмены, не ждут конца этой работы. Так же запускают работу, не связанную с событиями, например периодический опрос. Это обычная задача asyncio, но клиент пишет её ошибку в лог и отменяет её при `close()`. Задачу из `asyncio.create_task` клиент не знает и не отменит, а после закрытия её вызовы библиотеки бросают `ClientClosedError`. Поэтому фоновую работу, которая ходит в библиотеку, запускают через `client.start_task`.

```python
async def poll() -> None:
    while True:
        await temperature.set_value(read_sensor())
        await asyncio.sleep(10)


client.start_task(poll())
```

`await control.wait_value(expected, timeout)` ждёт, пока значение станет равным `expected`, или, если передана функция, пока она вернёт истину. Если значение уже такое, метод возвращается сразу, а по таймауту бросает `TimeoutError`. Он ждёт мимо очередей обработчиков, поэтому его можно вызывать из обработчика. У `pushbutton` значения нет, нажатие ждут через `on_value`. `None` метод не дожидается, стирание значения и пропажа контрола ожидание не завершают.

```python
relay = await client.get_control("wb-mr6c_10/K1", timeout=5)
await relay.set_value(True)
await relay.wait_value(True, timeout=5)
```


## Работа с MQTT вне конвенции

Для топиков вне конвенции есть сырые методы в `client.raw`.

| Вызов                                                           | Что делает                                                                                                                                                                                                         |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `await client.raw.subscribe(topic_filter, handler, qos=0)`      | постоянная подписка по фильтру с масками `+` и `#`. Возвращается, когда retained фильтра уже стоят в очереди обработчика, а без связи сразу, и retained придут после подключения. После переподключения подписка восстанавливается сама. Тот же обработчик на том же фильтре ничего не добавляет и возвращается, когда retained первого вызова в очереди. Общие подписки `$share/...` библиотека не принимает |
| `await client.raw.unsubscribe(handler)`                         | снимает обработчик со всех его фильтров                                                                                                                                                                            |
| `await client.raw.read(topic_filter)`                           | разово отдаёт то, что брокер хранит под фильтром сейчас, словарём «топик → тело». Фильтр, который уже слушает обработчик, читается без брокера                                                                    |
| `await client.raw.publish(topic, payload, qos=1, retain=False)` | публикует сообщение. Топик без масок, тело строкой, байтами, числом или `None`, но не `bool`                                                                                                                       |

```python
async def devices_changed(message: Message) -> None:
    devices = json.loads(message.payload)


await client.raw.subscribe("gateway/devices", devices_changed)
state = await client.raw.read("gateway/state")
await client.raw.publish("gateway/request/scan", '{"time": 60}')
```

Обработчик получает `Message` с полями `topic`, `payload` в байтах, `retain` и `qos`. `retain=True` у сообщений, которые брокер хранил и отдал при подписке, и так после каждого переподключения. Сообщение, опубликованное, когда подписка уже работает, приходит с `retain=False`, даже если его опубликовали с флагом retain.

Одну функцию можно подписать на несколько фильтров, у неё одна очередь, а сообщение, которое подходит под два её фильтра, приходит один раз. Второй обработчик на фильтре, на который клиент уже подписан, тоже получает всё, что брокер хранит под фильтром, без повторной подписки в брокере.

Сообщение с `retain=True` брокер хранит и отдаёт новым подписчикам. Без связи такая публикация ждёт в клиенте и уходит после переподключения, а после каждого переподключения клиент публикует свои retained-сообщения заново. Пустое сообщение с `retain=True` стирает топик, и клиент его больше не повторяет. Сообщение без retain получат только текущие подписчики, без связи `raw.publish` сразу бросает `BrokerDisconnectedError`.

Значения устройств конвенции меняют через объекты. Сырым методом можно послать команду в `/on` своего или чужого контрола, она дойдёт до драйвера или до `on_command` так же, как команда другого сервиса. Сырая запись прямо в топик значения в состояние клиента не попадает. У чужого контрола её перезапишет драйвер своей следующей публикацией, а у своего `control.value` разойдётся с тем, что лежит в брокере.

Отдельного метода удаления нет. Один топик стирается пустым retained, а много топиков по маске стираются так.

```python
for topic in await client.raw.read("/devices/old_device/#"):
    await client.raw.publish(topic, "", retain=True)
```

Сырой обработчик на ответ обычно снимают сразу после запроса. Иначе каждый вызов оставлял бы на фильтре ещё одну функцию.

```python
async def scan(client: Client, seconds: int) -> Any:
    answer = asyncio.get_running_loop().create_future()

    async def on_response(message: Message) -> None:
        if not answer.done():
            answer.set_result(json.loads(message.payload))

    await client.raw.subscribe("gateway/response/scan", on_response)
    try:
        await client.raw.publish("gateway/request/scan", json.dumps({"time": seconds}))
        return await asyncio.wait_for(answer, 10)
    finally:
        await client.raw.unsubscribe(on_response)
```


## Ошибки

| Ошибка                    | Когда                                                                                                                                              |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BrokerDisconnectedError` | вызову нужен ответ брокера, а связи нет или брокер не ответил вовремя. Это чтение брокера, в том числе в `create_device` и `get_control`, и сообщения без retain, то есть команды и нажатия. Изменения своих устройств без связи ошибки не дают и уходят после переподключения |
| `NotOwnError`             | действие владельца над чужим устройством, например `set_error` или `on_command`                                                                    |
| `ControlMissingError`     | действие с контролом, которого сейчас нет, или со своим устройством после его `remove()`                                                          |
| `DeviceTakenError`        | `create_device` без `force`, когда имя занято устройством другого драйвера                                                                         |
| `LoginRejectedError`      | брокер отверг логин при первом подключении                                                                                                         |
| `ClientClosedError`       | вызов после `close()` или ожидание брокера, которое прервал `close()`                                                                              |
| `TimeoutError`            | нужное значение, контрол или устройство не появились за `timeout`                                                                                 |
| `ValueError`              | неверное имя, топик, значение поля меты или адрес брокера, устройство или контрол уже созданы, второй клиент с тем же драйвером в процессе         |
| `TypeError`               | значение не подходит к типу контрола, у аргумента не тот тип, неизвестное поле меты, у обработчика не то число аргументов                          |
| `RuntimeError`            | повторный `connect()` подключённого клиента                                                                                                       |

Ошибки библиотеки наследуют `MqttLibError`, а `TimeoutError`, `ValueError`, `TypeError` и `RuntimeError` встроенные в Python. `TypeError` и `RuntimeError` означают ошибку в коде сервиса, ловить их не нужно. `DeviceTakenError` наследует ещё и `ValueError`. Ошибки aiomqtt до сервиса не доходят.

Исключение в обработчике событий библиотека пишет в лог и работает дальше, раздел [Исключения в обработчиках](#исключения-в-обработчиках). Вне обработчиков исключение уходит в вызывающий код, как у любой функции.


## Логи

Библиотека пишет в стандартный `logging`, вывод настраивает сервис. Имена логгеров идут по пути импорта, у библиотеки внутри пакета сервиса это `wb.<сервис>.wb_mqtt_lib.client`, `.device_sync`, `.subscriber`, `.publisher`, `.listeners` и `.state`, а строки aiomqtt и paho идут в `wb.<сервис>.wb_mqtt_lib.link.aiomqtt`. Обрыв связи клиент пишет одной строкой WARNING, сетевые строки paho о том же обрыве тоже понижены до WARNING.

Подробности работы библиотеки идут на уровне DEBUG. Включить его только для библиотеки при общем уровне INFO можно так.

```python
logging.basicConfig(level=logging.INFO)
logging.getLogger("wb.mqtt_example.wb_mqtt_lib").setLevel(logging.DEBUG)
```


## Когда нужен await

`await` нужен методам, которые ходят в брокер или ждут события. Это `connect`, `close`, `create_device`, `create_control`, `set_value`, `set_error`, `update_meta`, `remove`, `get_control`, `get_device`, `get_device_names`, `get_device_snapshot`, `remove_driver_devices`, `wait_value` и методы `client.raw`.

Без `await` вызывают то, что меняет только состояние внутри клиента. Это `on_*`, `remove_handler`, `client.start_task` и поля объектов.

Изменение своего устройства возвращается, когда брокер его принял, а без связи сразу, и сообщение уходит после переподключения. `set_value` и `set_error` своего устройства обычно возвращаются, не дожидаясь брокера, поэтому другой клиент сразу после возврата может ещё прочитать старое значение. Отмена `await` прерывает только ожидание, принятое изменение своего устройства уходит в брокер целиком.


## Ограничения

- Внутри конвенции публикации идут с QoS 1, подписки с QoS 0. Другой QoS задаётся только в `client.raw`.
- Своё устройство библиотека в брокере не слушает, правка извне держится до переподключения, раздел [Правки извне](#правки-извне).
